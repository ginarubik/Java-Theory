2.Mi a különbség az absztrakt osztály és az interfész között?
Az absztrakt osztály tartalmazhat megvalósítást és állapotot, míg az interfész egy szerződés, amely metódusok definícióját adja meg, és egy osztály több interfészt is implementálhat.
A Java nem támogatja a többszörös osztályöröklést, de interfészek implementálásával hasonló hatás érhető el, és az azonos metódusok ütközését felülírással kell kezelni.
Az interfész default metódusai példányon keresztül hívhatók, a static metódusok csak az interfész nevével, míg a private metódusok kizárólag belső segédmetódusként használhatók.
Abstract „részben kész osztály”:
lehet konkrét és absztrakt metódusa is
lehet mezője (state / állapot)
konstruktor is lehet
csak egy osztályt lehet örökölni
abstract class Animal {
    String name;
    Animal(String name) {
        this.name = name;
    abstract void sound();
    void sleep() {
        System.out.println("Sleeping...");
Gyerek osztály:
class Dog extends Animal {
    Dog(String name) {
        super(name);
    @Override
    void sound() {
        System.out.println("Woof");
„szerződés: mit kell tudnia egy osztálynak”
Jellemzők: csak metódus deklaráció (alapból)
nincs állapot (régebben), most már lehet default/static metódus
egy osztály több interfészt is implementálhat
interface Animal {    void sound();}
Implementálás:
class Dog implements Animal {    @Override    public void sound() {        System.out.println("Woof");    }}
Fő különbségek:
Absztrakt osztályInterface lehet: állapota(mezők)nincs (csak konstansok),lehet konstruktornincs konstruktorrészben implementált
teljesen absztrakt (alapból)csak 1 örökléstöbb interface is lehet extendsimplements
Absztrakt osztály:

Mikor melyiket használjuk?
Abstract class:
közös viselkedés + közös állapot
pl. Animal, Vehicle
Interface: viselkedés definiálása pl. Flyable, Comparable, Runnable
Abstract class → részleges implementáció + állapot
Interface → viselkedés szerződés
Az abstract class „mit tud már”, az interface „mit kell tudnia”.

3. Mi a "String immutability" jelentése Java-ban? 
A String immutability azt jelenti, hogy a Java String objektumok nem módosíthatók létrehozás után, minden változtatás új String objektumot hoz létre,míg a StringBuilder mutable, és 
ugyanazon objektumon belül módosítja a tartalmat, így hatékonyabb többszöri módosítás esetén.
String name = "Anna";
name = name + " Maria";
System.out.println(name); 
Eredmény: Anna Maria
Mi történt valójában?
"Anna" → eredeti String (nem változik)
"Anna Maria" → új String objektum

4. Hogyan működik a "Garbage Collection" Java-ban? 
Automatikusan felszabadítja azokat az objektumokat a heap memóriából, amelyekre már nincs hivatkozás, így optimalizálva a memóriahasználatot.
Nem determinisztikus, ezért a finalize() metódus végrehajtása nem garantált, és a System.gc() hívás sem biztosítja a GC azonnali futását.

        User u2 = new User(); // másik objektum
        u1 = null; // u1 objektum „szemét” lesz
👉 a Garbage Collector később eltávolítja az u1 által használt memóriát

9. Mi az a final, finally és finalize kulcsszó Java-ban?
A final módosító korlátozza a változtatást, a finally blokk mindig lefut kivételkezelés után, míg a finalize() metódust a Garbage Collector hívhatja meg objektum törlése előtt, 
de nem garantált a végrehajtása.
try → első blokk
throw → ugrás catch-be
finally → mindig lefut
finalize() → csak ha meghívják vagy a GC akarja
1. final példa (változó)
final int x = 10;
x = 20; // ❌ hiba
Példa (metódus):
class A {final void show(){System.out.println("Hello");}}class B extends A {// void show() {} ❌ nem lehet felülírni}
Példa (osztály): final class A {}// class B extends A {} ❌ nem lehet örökölni
finally👉 „mindig lefutó blokk”
try-catch után használjuk, akkor is lefut, ha van exception
try {int x = 10 / 0;} catch (Exception e) {System.out.println("Hiba");} finally {System.out.println("Mindig lefut");}
👉 a finally blokk mindig végrehajtódik
🔹 3. finalize()👉 „GC előtti takarítás” (elavult!)a Garbage Collection hívhatja meg, már nem ajánlott használni
class Test {@Override    protected void finalize() {System.out.println("Objektum törlés előtt");}}
⚠️ Fontos: nem garantált, hogy lefutJava 9+ óta elavult
finalfinallyfinalize()kulcsszó blokk metódus változhatatlanság mindig lefut, GC-hez kötött compile-timeruntime GC idő
final → nem módosítható
finally → mindig lefut
finalize() → elavult GC hook
👉 „final = fix, finally = mindig, finalize = régi GC metódus”

10. Hogyan kezeljük a kivételeket Java-ban?
A kivétel (exception) egy olyan esemény, amely futás közben hibát jelez (pl. osztás nullával, fájl nem található). A kivételek kezelése Java-ban az egyik alapvető eszköz a hibák biztonságos
és rendezett kezelésére. A cél az, hogy a program ne álljon le váratlanul, hanem kontrollált módon reagáljon a problémákra.
1.try-catch → hibák kezelése
finally → mindig lefut (pl. erőforrások lezárása)
throw → kivétel dobása manuálisan
throws → kivétel továbbadása
| `throw`             | `throws`              |
| ------------------- | --------------------- |
| kivételt dob        | kivételt jelez        |
| metóduson belül     | metódus fejlécében    |
| egy konkrét kivétel | több kivétel is lehet |
több catch ág
különböző hibák külön kezelése
try {String s = null;System.out.println(s.length());} catch (NullPointerException e) {System.out.println("Null hiba");} catch (Exception e) {System.out.println("Egyéb hiba");}
3. finally blokk👉 mindig lefut (pl. erőforrás lezárás)
try {int x = 10 / 2;} finally {System.out.println("Mindig lefut");}
4. throw (kivétel dobása)👉 saját hiba generálása
if (age < 18) {throw new IllegalArgumentException("Túl fiatal");}
5. throws (továbbadás)👉 metódus jelzi, hogy kivételt dobhat
public void readFile() throws IOException {FileReader file = new FileReader("test.txt");}
6. try-with-resources👉 automatikus erőforrás kezelés

🔑 Kivétel típusok:
Checked exception → kötelező kezelni (pl. IOException)
Unchecked exception → nem kötelező (pl. RuntimeException)
👉 Kivételkezelés eszközei:
try-catch → kezelés
finally → mindig lefut
throw → kivétel dobása
throws → kivétel továbbadása
👉 Cél: stabil, hibatűrő program működés.

11. Mi a különbség a "checked" és "unchecked" kivételek között?
Checked exception (ellenőrzött): fordításkor kezelni kell pl. IOException
Unchecked exception: futás közben jelentkezik
pl. NullPointerException, ArithmeticException
A különbség a **checked** és **unchecked** kivételek között a Java-ban az, hogy **kötelező-e őket kezelni fordításkor**.
Checked exception👉 „fordításkor kötelező kezelni”
* a fordító ellenőrzi
* **try-catch vagy throws kötelező**
* általában külső hibák (pl. fájl, hálózat)
import java.io.*;
public void readFile() {
    try {
        FileReader file = new FileReader("test.txt");
    } catch (IOException e) {
        System.out.println("Hiba: " + e.getMessage());
👉 ha nem kezeled → fordítási hiba
Unchecked exception👉 „nem kötelező kezelni”
* futásidőben történik
* nem kell try-catch
* programozási hibák
int x = 10 / 0; // ArithmeticException
👉 lefut, de runtime hibát dob
| Checked                 | Unchecked                     |
| ----------------------- | ----------------------------- |
| kötelező kezelni        | nem kötelező                  |
| compile-time ellenőrzés | runtime hiba                  |
| Exception leszármazott  | RuntimeException leszármazott |
# 🔗 Példa throws-szal:
public void readFile() throws IOException {
    FileReader file = new FileReader("test.txt");
👉 itt nem kezeljük, csak továbbadjuk
# 🔹 Tipikus példák:
## Checked:
* IOException
* SQLException
## Unchecked:
* NullPointerException
* IllegalArgumentException
* ArithmeticException
# 🔥 Röviden:
* **Checked** → kötelező kezelni (külső hibák)
* **Unchecked** → nem kötelező (programozási hibák)
👉 „checked = compiler figyel, unchecked = runtime meglepetés”

40. Hogyan működik a hashCode() és equals() metódus?
Objektumok összehasonlítására és hash-alapú adatszerkezetek (pl. HashMap, HashSet) működésére szolgálnak.
Az equals() metódus azt vizsgálja, hogy két objektum tartalmilag egyenlő-e.
Az Object osztályban alapértelmezés szerint referencia-összehasonlítást végez(==).
Gyakran felül kell írni, hogy a mezők alapján hasonlítson.
a.equals(b)→ true, ha a két objektum tartalma megegyezik.
A hashCode() metódus egy egész számot ad vissza, amely az objektumhoz tartozó hash érték.
Hash-alapú gyűjtemények használják a gyors kereséshez.
Az objektumot egy „bucket”-be sorolja a hash érték alapján.
A két metódus kapcsolata (fontos szabály)
A Java szabály (contract): ha két objektum equals() szerint egyenlő, akkor a hashCode()-juk is azonos kell legyen.
a.equals(b) == true  ⇒  a.hashCode() == b.hashCode()
Fordítva nem kötelező igaz (hash ütközés előfordulhat).
Miért kell mindkettőt felülírni?
Hash-alapú struktúrák működése:
hashCode() alapján kiválasztja a tárolási helyet
equals()-szal pontosan ellenőrzi az egyenlőséget
Ha csak az egyiket írjuk felül, hibás működés léphet fel (pl. HashSet nem találja meg az elemet).
equals() → logikai (tartalmi) összehasonlítás
hashCode() → hash érték számítása
Egyenlő objektumoknak azonos hashCode-dal kell rendelkezniük
Mindkettőt együtt kell felülírni hash-alapú kollekciók esetén

51. Mi az a HashSet?

53. Mi a különbség a Queue és a Deque között?
A Queue és a (Double-Ended Queue) két rokon adatszerkezet, de eltérnek abban, hogy honnan lehet elemeket hozzáadni és eltávolítani
Queue (sor): FIFO elv(First In, First Out)
Az elemek a végére kerülnek be (enqueue) és az elejéről kerülnek ki(dequeue)
Olyan, mint egy sorban állás: [Első] A → B → C [Utolsó]
Ha kiveszünk egy elemet → A távozik
Deque (kétvégű sor)
Mindkét végén lehet műveleteket végezni
Lehet: elöl és hátul is beszúrni, elöl és hátul is törölni
[Első] A ↔ B ↔ C [Utolsó] betehetünk előre vagy hátra
kivehetünk előről vagy hátulról
Queue→ csak egy irányból kezelhető(FIFO)
Deque→ két irányból kezelhető (rugalmasabb)
A Deque általánosabb struktúra, amely képes úgy működni, mint egy Queue (ha csak az egyik végét használjuk).
Queue = egyszerű sor (FIFO)
Deque= kétvégű sor (több műveleti lehetőség)

58. Mi az a String pool?
A Java memóriakezelésének egy speciális része, amely a **String objektumok hatékony tárolását** szolgálja.
## 🔹 Lényege:
A String pool egy olyan memóriaterület, ahol a Java **eltárolja az azonos szövegeket**, hogy ne jöjjenek létre felesleges duplikátumok.

```java id="q8t2lv"

## 🔹 Fontos metódus:
* `intern()`

System.out.println(b == "hello"); // true
```👉 Az `intern()` visszaadja a poolban lévő példányt.
## 🔹 Előnyei:
* **Memóriahatékony**
* **Gyorsabb összehasonlítás** (`==` is működhet)
## ⚠️ Fontos:
* String összehasonlításnál általában **.equals()**-t használunk, nem `==`-t
## 🔹 Röviden:
A String pool egy **speciális tárhely a Java-ban**, ahol az azonos String értékek **megosztva, duplikáció nélkül** kerülnek tárolásra.

Normál esetben a kódod „maga hívja meg” a szükséges objektumokat és függőségeket.
IoC esetén viszont:
👉 **a framework hozza létre és adja oda az objektumokat neked**
## 🔹 Hagyományos megközelítés:
Service service = new Service();
Controller controller = new Controller(service);
👉 Te hozod létre és kezeled a függőségeket.
## 🔹 IoC megközelítés:
A framework (pl. Spring Framework) csinálja:
@Autowired
Service service;
👉 A Spring „beinjectálja” a Service-t.
## 🔹 Hogyan valósul meg?
Az IoC leggyakoribb formája a **Dependency Injection (DI)**.
## 🔹 Előnyei:
* **Lazább kapcsolatok (loose coupling)**
* **Könnyebb tesztelhetőség**
* **Jobb karbantarthatóság**
* **Rugalmasabb architektúra**
## 🔹 Hol találkozhatsz vele?
* Spring (Java)
* .NET Core
* Angular
* sok modern framework
## 🔑 Röviden:
Az Inversion of Control azt jelenti, hogy **nem te irányítod közvetlenül az objektumok létrehozását és kezelését, hanem egy framework veszi át ezt a feladatot**.

64. Milyen injection típusok vannak?
Az **Dependency Injection** (DI) az **Inversion of Control** egyik megvalósítása, ahol az objektumok függőségeit kívülről kapják meg.
A DI-nak több típusa van a Java és más OOP nyelvek világában.
## 🔹 1. Constructor Injection (konstruktoros injekció)
* A függőségeket a **konstruktoron keresztül kapja az osztály**
* Ez a **leggyakrabban ajánlott** módszer
### Példa:
class Service {
class Controller {
    private final Service service;

    public Controller(Service service) {
        this.service = service;
👉 Előnye:
* kötelező függőségek biztosak
* immutable (final mezők)
* tesztelhető
## 🔹 2. Setter Injection (setteres injekció)
* A függőséget **setter metódussal adjuk át**
class Controller {
    private Service service;
    public void setService(Service service) {
        this.service = service;
👉 Előnye:
* opcionális függőségekhez jó
* később is beállítható
👉 Hátrány:
* az objektum ideiglenesen „félkész” állapotban lehet
## 🔹 3. Field Injection (mező injekció)
* A függőség **közvetlenül a mezőre kerül**
* Gyakori pl. Springben
### Példa:
class Controller {
    @Autowired
    private Service service;
👉 Előnye:
* nagyon egyszerű használat
👉 Hátrány:
* nehezebb tesztelni
* rejtett függőségek
* erősen framework-függő
| Típus                 | Jellemző                | Ajánlás                      |
| --------------------- | ----------------------- | ---------------------------- |
| Constructor Injection | Konstruktoron keresztül | ⭐ Legjobb                    |
| Setter Injection      | Setter metódussal       | Opcionális függőségekhez     |
| Field Injection       | Közvetlen mező          | Kényelmes, de kevésbé tiszta |
## 🔹 Röviden:
A dependency injection típusai:
* **konstruktoros**
* **setteres**
* **mező (field) injekció**
👉 A legjobb gyakorlat általában a **constructor injection**.

67. Hogyan használjuk a @RestController annotációt a Spring Boot alkalmazásokban, és mi

A **Spring Boot** alkalmazásokban a **@RestController** és a **@Controller** annotációk a webes réteg (presentation layer) részei, de más célt szolgálnak.
## 🔹 @Controller, a klasszikus Spring MVC vezérlő.
### 🔸 Mire használjuk?
* HTML oldalak visszaadására (view-k)
* JSP / Thymeleaf sablonokkal dolgozik

68. Mi a különbség a @RequestParam és a @PathVariable annotációk között a Spring Boot-ban?
A **Spring Boot**-ban a **@RequestParam** és a **@PathVariable** két különböző módja annak, hogy adatot vegyünk át HTTP kérésből egy controllerben.
## 🔹 @PathVariable
👉 Az URL útvonalából (path-ból) veszi az értéket
### 📌 Mire használjuk?
* konkrét erőforrás azonosítására
* RESTful URL-eknél
@GetMapping("/users/{id}")
public String getUser(@PathVariable Long id) {
    return "User id: " + id;
### 🔗 Hívás:
/users/5
👉 Az `id = 5` az URL része
## 🔹 @RequestParam
👉 Az URL query paraméteréből veszi az értéket
### 📌 Mire használjuk?
* szűrés, keresés, opcionális paraméterek
@GetMapping("/users")
public String getUser(@RequestParam String name) {
    return "Name: " + name;
### 🔗 Hívás:
/users?name=Anna
👉 A `name = Anna` query paraméterből jön
| Tulajdonság | @PathVariable        | @RequestParam    |
| ----------- | -------------------- | ---------------- |
| Hely        | URL path             | Query string     |
| Példa URL   | /users/5             | /users?name=Anna |
| Használat   | erőforrás azonosítás | szűrés, keresés  |
| Kötelezőség | általában kötelező   | lehet opcionális |
## 🔗 Egyszerű szabály:
* **PathVariable** → „melyik objektum?”
* **RequestParam** → „milyen feltételekkel?”
## 🔹 Röviden:
* **@PathVariable** → URL része (pl. /users/1)
* **@RequestParam** → URL paraméter (pl. ?name=Anna)
👉 REST API-ban a kettő együtt gyakran használatos:
azonosítás + szűrés kombinációjára.

71. Mi az a @ResponseBody annotáció, és hogyan használjuk a válasz testreszabására egy 
REST API-ban a Spring Boot használatával?
A **@ResponseBody** a Spring Boot (és Spring MVC) egyik fontos annotációja, amely azt mondja meg, hogy a metódus visszatérési értéke **közvetlenül a HTTP válasz törzsébe (body)** kerüljön, ne pedig egy nézet (view) neve legyen.
## 🔹 Mit csinál pontosan?
Alapból egy **@Controller** esetén:
* a visszatérési érték → **nézetnév (pl. HTML oldal)**
Ha viszont használjuk a `@ResponseBody`-t:
* a visszatérési érték → **JSON / XML formában a kliensnek megy vissza**
@Controller
public class UserController {
    @GetMapping("/user")
    @ResponseBody
    public String getUser() {
        return "Hello User";
👉 A válasz: Hello User
## 🔹 Objektum visszaadása (JSON)
@GetMapping("/user")
@ResponseBody
public User getUser() {
    return new User("Anna", 25);
👉 A Spring automatikusan JSON-ra alakítja:
{
  "name": "Anna",
  "age": 25
## 🔹 Hogyan működik?
* A Spring egy ún. **HTTP message convertert** használ
* (pl. Jackson) → Java objektum → JSON
## 🔹 Kapcsolat a @RestController-rel
A **@RestController** valójában:
@Controller + @ResponseBody
👉 Ezért REST API-kban általában nem kell külön kiírni a `@ResponseBody`-t.
## 🔹 Mikor használjuk?
* REST API-knál
* amikor **adatot (JSON/XML)** akarunk visszaadni, nem HTML oldalt
## 🔑 Röviden:
* **@ResponseBody** → a visszatérési érték a HTTP válasz törzsébe kerül
* JSON/XML választ készít
* REST API-knál alapvető
👉 Gyakorlatban sokszor a **@RestController** kiváltja.

72. Hogyan tudnál adatot küldeni a szervernek HTTP segítségével? (url, header, body)
HTTP-n keresztül többféleképpen tudunk adatot küldeni a szervernek, attól függően, hogy **hol helyezzük el az adatot a kérésben**. Ez a működés alapja például egy REST API kommunikációnak.
## 🔹 1. URL-ben (path vagy query paraméter)
### 📌 Path paraméter (URL része)
GET /users/5
👉 itt az `5` az adat
### 📌 Query paraméter
GET /users?name=Anna&age=25
👉 kulcs-érték párok az URL végén
### Mikor használjuk?
* lekérdezésekhez
* szűréshez
* kisebb adatoknál
## 🔹 2. Header-ben
A HTTP header-ek metaadatokat tartalmaznak.
GET /users
Authorization: Bearer token123
Content-Type: application/json
### Mikor használjuk?
* autentikáció (pl. token)
* tartalomtípus megadása
* kliens információk
## 🔹 3. Body-ban
A request body-ban **nagyobb vagy strukturált adatokat** küldünk.
POST /users
Content-Type: application/json
  "name": "Anna",
  "age": 25
### Mikor használjuk?
* új adat létrehozásakor (POST)
* frissítésnél (PUT, PATCH)
* komplex objektumoknál
| Hely   | Mire jó         | Példa               |
| ------ | --------------- | ------------------- |
| URL    | egyszerű adatok | /users?name=Anna    |
| Header | metaadat        | Authorization token |
| Body   | komplex adatok  | JSON objektum       |
## 🔹 Gyakorlatban (Spring Boot):
* URL → `@PathVariable`, `@RequestParam`
* Header → `@RequestHeader`
* Body → `@RequestBody`
## 🔹 Röviden:
Adatot HTTP-n keresztül így küldünk:
* **URL-ben** → azonosítás, szűrés
* **Header-ben** → metaadat (pl. auth)
* **Body-ban** → tényleges adat (pl. JSON)
👉 A választás attól függ, milyen típusú adatot és milyen célból küldünk.

73. Mik a státusz kódok főbb típusai, és mire használják őket?
A HTTP **státuszkódok** a szerver válaszának rövid, szabványos jelzései, amelyek megmondják, hogy a kérés **sikeres volt-e, vagy milyen hiba történt**. Ezek alapvető részei minden HTTP kommunikációnak és REST API működésnek.
## 🔹 Főbb státuszkód kategóriák
A kódok első számjegye jelzi a típust:
### 🟢 1xx – Információs
* A kérés feldolgozása folyamatban van
👉 Ritkán használjuk a gyakorlatban
### 🔵 2xx – Sikeres
👉 A kérés sikeresen teljesült
* **200 OK** → sikeres lekérdezés
* **201 Created** → új erőforrás létrejött
* **204 No Content** → sikeres, de nincs válasz tartalom
### 🟡 3xx – Átirányítás
👉 A kliensnek máshová kell mennie
* **301 Moved Permanently** → végleges átirányítás
* **302 Found** → ideiglenes átirányítás
### 🔴 4xx – Kliens hiba
👉 A hiba a kliens kérésében van
* **400 Bad Request** → hibás kérés
* **401 Unauthorized** → nincs hitelesítés
* **403 Forbidden** → nincs jogosultság
* **404 Not Found** → nem található erőforrás
### 🔥 5xx – Szerver hiba
👉 A hiba a szerver oldalán van
* **500 Internal Server Error** → általános hiba
* **502 Bad Gateway**
* **503 Service Unavailable** → szolgáltatás nem elérhető
## 🔑 Mire használjuk?
* kliens és szerver közötti kommunikáció jelzésére
* hibakezelésre
* API-k viselkedésének szabályozására
* frontend döntésekhez (pl. hibaüzenet megjelenítés)
GET /users/5
→ 200 OK
GET /users/999
→ 404 Not Found
## 🔹 Röviden:
* **1xx** → információ
* **2xx** → siker
* **3xx** → átirányítás
* **4xx** → kliens hiba
* **5xx** → szerver hiba
👉 A státuszkódok segítenek gyorsan megérteni, mi történt a kérés során.

75. Mit jelentenek a 3-al kezdődő HTTP státusz kódok? Mi történik ha egy ilyen választ kap a 
browser a szervertől? 
A **3xx HTTP státuszkódok** a HTTP válaszok **átirányítást (redirection)** jelentenek. Ez azt jelenti, hogy a kért erőforrás **nem azon az URL-en érhető el**, ahol a kliens kereste, hanem máshol.
## 🔹 Mit jelent pontosan?
A szerver azt mondja:
👉 „Az erőforrás máshol van, menj oda!”
## 🔹 Gyakoribb 3xx kódok:
* **301 Moved Permanently**
  → végleges áthelyezés (SEO szempontból is fontos)
* **302 Found**
  → ideiglenes átirányítás
* **303 See Other**
  → másik URL-en kell lekérni (pl. POST után GET)
* **304 Not Modified**
  → nincs változás (cache használható)
* **307 Temporary Redirect**
  → ideiglenes, metódus megmarad
## 🔹 Mi történik a böngészőben?
Ha a browser egy 3xx választ kap:
1. Megnézi a válasz **Location headerét**
2. Automatikusan új kérést küld az új URL-re
3. A felhasználó ezt általában **nem is veszi észre*
GET /old-page
→ 301 Moved Permanently
Location: /new-page
👉 A böngésző automatikusan:
GET /new-page
## 🔹 Különleges eset – 304:
* Nem történik új letöltés
* A böngésző a **cache-ben lévő verziót használja**
## 🔑 Röviden:
* **3xx kódok = átirányítás**
* A szerver új URL-t ad meg
* A böngésző automatikusan követi ezt
👉 A felhasználó legtöbbször csak annyit lát: „betöltött az oldal”, de a háttérben átirányítás történt.

77. Mit értünk REST API alatt? 
A **REST API** egy olyan webes API, amely a **REST (Representational State Transfer)** architektúrális elveit követi, és HTTP-n keresztül teszi lehetővé az adatok elérését és kezelését.
## 🔹 Egyszerűen:
👉 A REST API egy mód arra, hogy a kliens (pl. frontend) és a szerver **HTTP kéréseken keresztül kommunikáljon**.
## 🔹 Alapelvek:
### 1. Erőforrás-alapú
* Minden adat egy **resource (erőforrás)**
* URL-ekkel azonosítjuk
/users
/users/5
### 2. HTTP metódusok használata
* **GET** → lekérdezés
* **POST** → létrehozás
* **PUT / PATCH** → módosítás
* **DELETE** → törlés
### 3. Stateless (állapotmentes)
* Minden kérés **független**
* A szerver nem tárol kliens állapotot
### 4. Egységes interfész
* Szabványos HTTP használat
* kiszámítható működés
### 5. Reprezentációk
* Az adatokat általában **JSON** formátumban küldjük
GET /users/5
→ 200 OK
  "id": 5,
  "name": "Anna"
## 🔹 Hol használjuk?
* Web alkalmazások (frontend ↔ backend)
* Mobil appok
* Microservice-ek közötti kommunikáció
## 🔑 Előnyei:
* egyszerű és jól skálázható
* platformfüggetlen
* könnyen tesztelhető
* széles körben támogatott
## 🔹 Röviden:
A REST API egy **HTTP-alapú kommunikációs szabvány**, ahol:
* URL-ek → erőforrások
* HTTP metódusok → műveletek
* JSON → adatcsere
👉 Ez a modern webes alkalmazások egyik legfontosabb alapja.

78. Mi a különbség az autentikáció és az autorizáció között?
Az **autentikáció** és az **autorizáció** két alapvető biztonsági fogalom, gyakran együtt használjuk őket pl. Spring Security alapú rendszerekben, de **nem ugyanazt jelentik**.
## 🔹 Autentikáció (Authentication)
👉 „Ki vagy?”
### Mit jelent?
* A felhasználó **azonosítása**
* Annak ellenőrzése, hogy valóban az-e, akinek mondja magát
### Példák:
* felhasználónév + jelszó
* biometrikus azonosítás
* token (pl. JWT)
👉 Eredmény: **a rendszer tudja, hogy ki vagy**
## 🔹 Autorizáció (Authorization)
👉 „Mit tehetsz meg?”
### Mit jelent?
* Jogosultságok ellenőrzése
* Meghatározza, hogy egy felhasználó **milyen erőforrásokhoz férhet hozzá**
### Példák:
* admin → mindenhez hozzáfér
* user → csak saját adataihoz
👉 Eredmény: **mit csinálhatsz a rendszerben**
## 🔑 Fő különbség:
| Fogalom      | Kérdés       | Jelentés    |
| ------------ | ------------ | ----------- |
| Autentikáció | Ki vagy?     | Azonosítás  |
| Autorizáció  | Mit tehetsz? | Jogosultság |
## 🔗 Hogyan működnek együtt?
1. **Autentikáció** → bejelentkezés
2. **Autorizáció** → hozzáférés ellenőrzése
👉 Nem tudsz jogosultságot kapni, ha előtte nem azonosítottad magad.
## 🔹 Röviden:
* **Autentikáció** = azonosítás
* **Autorizáció** = jogosultságkezelés
👉 „Ki vagy?” vs „Mit tehetsz?”

79. Mit jelent a DDL és a DML? Mik tartoznak ezekbe?
A **DDL** és a **DML** az SQL két alapvető parancscsoportja, amelyek különböző feladatokra szolgálnak az adatbázis-kezelésben.
# 🔹 DDL (Data Definition Language)
👉 „Adatszerkezet definiálása”
### Mire használjuk?
* adatbázis **struktúrájának létrehozása és módosítása**
### Ide tartozó parancsok:
* **CREATE** → tábla létrehozása
* **ALTER** → tábla módosítása
* **DROP** → tábla törlése
* **TRUNCATE** → tábla kiürítése
CREATE TABLE users (
    id INT,
    name VARCHAR(100)
👉 Itt a struktúrát hozod létre, nem az adatot kezeled.
# 🔹 DML (Data Manipulation Language)
👉 „Adatok kezelése”
### Mire használjuk? * az adatbázisban lévő **adatok módosítása**
### Ide tartozó parancsok:
* **INSERT** → adat beszúrása
* **UPDATE** → adat módosítása
* **DELETE** → adat törlése
* **SELECT** → adat lekérdezése
INSERT INTO users (id, name)
VALUES (1, 'Anna');
👉 Itt már konkrét adatokat kezelünk.
| DDL           | DML              |
| ------------- | ---------------- |
| Struktúra     | Adat             |
| Táblák, sémák | Sorok (rekordok) |
| CREATE, ALTER | INSERT, UPDATE   |
## 🔹 Röviden:
* **DDL** → adatbázis szerkezetének kezelése
* **DML** → adatok kezelése az adatbázisban
👉 Egyszerűen:
**DDL = „mit hozok létre”**
**DML = „mit csinálok az adatokkal”**

80. Mi a tranzakció?
Az **tranzakció** egy olyan műveletsor az adatbázisban, amelyet **egyetlen egységként kezelünk**: vagy **minden lépése sikeresen végrehajtódik**, vagy **egyik sem**.

👉 „Minden vagy semmi” elv
Banki utalás:
1. pénz levonása az egyik számláról
2. pénz jóváírása a másikon
👉 Ha az egyik lépés hibázik:
* az egész művelet visszagörgetődik (rollback)
## 🔹 Fő tulajdonságok (ACID)
### 🔸 A – Atomicity (atomosság)
* vagy minden lefut, vagy semmi

* az adatbázis mindig érvényes állapotban marad
### 🔸 I – Isolation (izoláció)
* párhuzamos tranzakciók nem zavarják egymást

* sikeres művelet után az adatok megmaradnak

* **BEGIN** → tranzakció indítása
* **COMMIT** → véglegesítés
* **ROLLBACK** → visszavonás

UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;

## 🔹 Röviden:
A tranzakció egy **biztonságos műveleti egység**, amely:
* garantálja az adatok helyességét
* hibánál visszaállítja az eredeti állapotot
👉 „Minden sikerül, vagy semmi sem történik.”

85. Mi a különbség a LEFT JOIN és a RIGHT JOIN között SQL-ben? 
A **LEFT JOIN** és a **RIGHT JOIN** az SQL-ben (SQL) nagyon hasonló műveletek, a különbség az, hogy **melyik táblát tekintjük „fő” (megtartott) táblának**.
## 🔹 LEFT JOIN
👉 „Bal tábla minden sora megmarad”
* A bal oldali tábla **összes sora szerepel az eredményben**
* A jobb oldali tábla csak akkor, ha van egyezés
* Ha nincs egyezés → NULL értékek
SELECT users.name, orders.id
FROM users
LEFT JOIN orders ON users.id = orders.user_id;
👉 Minden user megjelenik, akkor is, ha nincs rendelése
## 🔹 RIGHT JOIN 👉 „Jobb tábla minden sora megmarad”
* A jobb oldali tábla **összes sora szerepel**
* A bal oldali csak egyezés esetén
* Ha nincs egyezés → NULL
SELECT users.name, orders.id
FROM users
RIGHT JOIN orders ON users.id = orders.user_id;
👉 Minden rendelés megjelenik, akkor is, ha nincs hozzá user
| LEFT JOIN             | RIGHT JOIN             |
| --------------------- | ---------------------- |
| bal tábla minden sora | jobb tábla minden sora |
| jobb oldal lehet NULL | bal oldal lehet NULL   |
| gyakoribb             | ritkábban használt     |
## 🔗 Fontos megjegyzés:
👉 A RIGHT JOIN **mindig kiváltható LEFT JOIN-nal**, ha felcseréljük a táblákat:
-- RIGHT JOIN
A RIGHT JOIN B
-- ugyanaz, mint:
B LEFT JOIN A
## 🔹 Röviden:
* **LEFT JOIN** → bal tábla minden sora
* **RIGHT JOIN** → jobb tábla minden sora
👉 A különbség csak abban van, melyik tábla adja az „alap” rekordokat.

86. Mi a GROUP BY SQL utasítás szerepe, és hogyan használható az aggregáló 
függvényekkel? 
A **GROUP BY** az SQL-ben (SQL) arra szolgál, hogy az adatokat **csoportokba rendezze egy vagy több oszlop alapján**, és ezeken a csoportokon **aggregáló függvényeket** tudjunk futtatni.
# 🔹 Mire jó a GROUP BY?
👉 Adatok csoportosítására használjuk, például:
* városok szerint
* kategóriák szerint
* felhasználók szerint
# 🔹 Alap példa
SELECT city, COUNT(*)
FROM users
GROUP BY city;
👉 Mit csinál?
* városonként csoportosít
* megszámolja hány user van városonként
## 🔹 Eredmény:
Budapest  10
Debrecen  5
Szeged    8
# 🔹 Kapcsolat aggregáló függvényekkel
A GROUP BY-t mindig **aggregáló függvényekkel együtt használjuk**, mint:
* **COUNT**
* **SUM**
* **AVG**
* **MIN**
* **MAX**
# 🔹 Példa SUM-mal
SELECT department, SUM(salary)
FROM employees
GROUP BY department;
👉 Osztályonként összes fizetés
# 🔹 Példa AVG-vel
SELECT department, AVG(salary)
FROM employees
GROUP BY department;
👉 Osztályonként átlagfizetés
# 🔹 FONTOS szabály
Ha GROUP BY-t használsz: 👉 minden SELECT-ben szereplő oszlopnak vagy:
* csoportosítottnak kell lennie
* vagy aggregáló függvényben kell szerepelnie
# 🔹 GROUP BY + HAVING (plusz info)
A csoportokra szűrést a **HAVING** végzi:
SELECT city, COUNT(*)
FROM users
GROUP BY city
HAVING COUNT(*) > 5;
👉 csak azok a városok, ahol több mint 5 user van
# 🔑 Röviden:
* **GROUP BY** → adatok csoportosítása
* **Aggregáló függvényekkel együtt használjuk**
* Pl. COUNT, SUM, AVG
👉 Segítségével összesítéseket készítünk adatcsoportokra.

87. Mi a különbség a WHERE és a HAVING utasítások között SQL-ben?
A **WHERE** és a **HAVING** az SQL-ben (SQL) mindkettő szűrésre szolgál, de **különböző fázisban és más célra használjuk őket**.
# 🔹 WHERE 👉 „Sor szintű szűrés”
* **a táblában lévő egyedi sorokat szűri**
* még a csoportosítás (GROUP BY) előtt működik
SELECT *
FROM users
WHERE age > 18;
👉 csak a 18 év feletti felhasználók
# 🔹 HAVING 👉 „Csoport szintű szűrés”
* **GROUP BY után szűr**
* aggregált eredményeket szűr (pl. COUNT, SUM)
SELECT city, COUNT(*)
FROM users
GROUP BY city
HAVING COUNT(*) > 5;
👉 csak azok a városok maradnak, ahol több mint 5 user van
# 🔑 Fő különbség:
| WHERE                    | HAVING               |
| ------------------------ | -------------------- |
| sorokat szűr             | csoportokat szűr     |
| GROUP BY előtt           | GROUP BY után        |
| nem használ aggregátumot | használ aggregátumot |
# 🔗 Logikai sorrend SQL-ben:
1. FROM
2. WHERE
3. GROUP BY
4. HAVING
5. SELECT
SELECT city, COUNT(*)
FROM users
WHERE age > 18
GROUP BY city
HAVING COUNT(*) > 5;
👉 először szűri a felnőtteket (WHERE),
👉 majd városonként csoportosít,
👉 végül csak a nagy csoportokat hagyja meg (HAVING)
# 🔹 Röviden:
* **WHERE** → egyedi sorokat szűr
* **HAVING** → csoportosított eredményeket szűr
👉 A WHERE „előszűr”, a HAVING „utószűr”.

* aggregált eredményeket szűr (pl. COUNT, SUM)
SELECT city, COUNT(*)
FROM users
GROUP BY city
HAVING COUNT(*) > 5;
👉 csak azok a városok maradnak, ahol több mint 5 user van
| WHERE                    | HAVING               |
| ------------------------ | -------------------- |
| sorokat szűr             | csoportokat szűr     |
| GROUP BY előtt           | GROUP BY után        |
| nem használ aggregátumot | használ aggregátumot |
# 🔗 Logikai sorrend SQL-ben:
1. FROM
2. WHERE
3. GROUP BY
4. HAVING
5. SELECT
SELECT city, COUNT(*)
FROM users
WHERE age > 18
GROUP BY city
HAVING COUNT(*) > 5;
👉 először szűri a felnőtteket (WHERE),
👉 majd városonként csoportosít,
👉 végül csak a nagy csoportokat hagyja meg (HAVING)
# 🔹 Röviden:
* **WHERE** → egyedi sorokat szűr
* **HAVING** → csoportosított eredményeket szűr
👉 A WHERE „előszűr”, a HAVING „utószűr”.
👉 minden rekord a bal táblából + egyezések a jobb táblából

LEFT JOIN orders ON users.id = orders.user_id;

👉 minden rekord a jobb táblából

FROM users
RIGHT JOIN orders ON users.id = orders.user_id;
👉 minden rendelés megjelenik, még ha nincs user (ritkábban használják)

👉 minden kombináció minden sorral
SELECT users.name, products.name
FROM users
CROSS JOIN products;
👉 „szorzat” jellegű eredmény

JOIN: 👉 több tábla adatainak összekapcsolására szolgál

88. Mi a PRIMARY KEY és a FOREIGN KEY, és hogyan használjuk őket adatbázisokban?
A **PRIMARY KEY** és a **FOREIGN KEY** az SQL-ben (SQL) az adatbázisok **kapcsolatainak és integritásának biztosítására** szolgálnak.
# 🔹 PRIMARY KEY
👉 „Egyedi azonosító egy táblában”
* Minden rekordot **egyértelműen azonosít**
* **Nem lehet NULL**
* **Nem ismétlődhet**
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(100)
👉 az `id` minden usernél egyedi
* rekordok egyértelmű azonosítása
* kapcsolatok létrehozása más táblákkal
# 🔹 FOREIGN KEY
👉 „Hivatkozás egy másik tábla elsődleges kulcsára”
* kapcsolatot hoz létre két tábla között
* biztosítja az **adatbázis integritást**
CREATE TABLE orders (
    id INT PRIMARY KEY,
    user_id INT,
    FOREIGN KEY (user_id) REFERENCES users(id)
👉 minden rendelés egy userhez tartozik
* relációk létrehozása táblák között
* adatkonzisztencia biztosítása
* nem létező adatra hivatkozás megakadályozása
 PRIMARY KEY           | FOREIGN KEY                       |
| --------------------- | --------------------------------- |
| egy tábla azonosítója | másik tábla kulcsára hivatkozik   |
| egyedi                | ismétlődhet                       |
| nem lehet NULL        | lehet NULL (opcionális kapcsolat) |
| identitás             | kapcsolat                         |
# 🔗 Kapcsolat példa:
* users.id → PRIMARY KEY
* orders.user_id → FOREIGN KEY
👉 egy userhez több order tartozhat (1:N kapcsolat)
# 🔹 Röviden:
* **PRIMARY KEY** → egy tábla egyedi azonosítója
* **FOREIGN KEY** → kapcsolat másik tábla kulcsához
👉 Ezek együtt biztosítják a relációs adatbázisok strukturált működését.

89. Hogyan működik az AUTO_INCREMENT attribútum SQL-ben, és milyen típusú adatok

Az **AUTO_INCREMENT** egy SQL (SQL) tulajdonság, amely automatikusan **növekvő számértéket generál egy oszlop számára**, amikor új rekord kerül beszúrásra.

* Nem kell kézzel megadni az ID-t

CREATE TABLE users (

INSERT INTO users (name) VALUES ('Anna');
INSERT INTO users (name) VALUES ('Béla');

1 - Anna
2 - Béla
# 🔹 Milyen típusoknál használható?
👉 AUTO_INCREMENT általában:
* **egész szám típusoknál működik**
### Gyakori típusok:
* INT
* BIGINT
* SMALLINT (ritkábban)
* elsődleges kulcs (PRIMARY KEY) generálására
* egyedi azonosítók automatikus létrehozására
* csak **egy AUTO_INCREMENT oszlop lehet táblánként**
* általában **PRIMARY KEY-hez kötjük**
* nem lehet manuálisan ismétlődő érték
* MySQL → AUTO_INCREMENT
* PostgreSQL → SERIAL / IDENTITY
* SQL Server → IDENTITY
# 🔹 Röviden:
Az AUTO_INCREMENT:
👉 automatikusan növekvő számot generál új rekordokhoz
👉 csak numerikus mezőkön használható
👉 leggyakrabban PRIMARY KEY-hez használjuk
👉 Célja: egyedi azonosítók egyszerű létrehozása.

90. Mit jelent a NULL érték SQL-ben, és hogyan kezelhetjük azt?
A **NULL** az SQL-ben (SQL) azt jelenti, hogy egy mezőben **nincs adat / ismeretlen / nincs érték**.
A NULL nem:
* nem 0
* nem üres string (`""`)
* nem false
👉 Hanem: **„nincs érték megadva”**
SELECT name, age FROM users;
Eredmény:
Anna   25
Béla   NULL
👉 Béla életkora nincs megadva
## ⚠️ 1. NULL nem hasonlítható egyszerűen
WHERE age = NULL   -- ❌ hibás
👉 helyette:
WHERE age IS NULL
## ⚠️ 2. NULL műveletek eredménye is NULL lehet
SELECT 10 + NULL;  -- eredmény: NULL
## 🔸 1. IS NULL / IS NOT NULL
SELECT * FROM users WHERE age IS NULL;
SELECT * FROM users WHERE age IS NOT NULL;
## 🔸 2. COALESCE (alapérték adása)
👉 ha NULL, adjon vissza más értéket
SELECT COALESCE(age, 0) FROM users;
👉 NULL helyett 0 jelenik meg
## 🔸 3. IFNULL / NVL (DB-függő)
* MySQL: IFNULL
* Oracle: NVL
SELECT IFNULL(age, 0) FROM users;
## 🔸 4. Aggregációknál
* **COUNT(*)** → számolja a NULL-t is
* **COUNT(oszlop)** → NULL-t nem számolja
# 🔑 Összefoglalás:
| Fogalom  | Jelentés                 |
| -------- | ------------------------ |
| NULL     | nincs / ismeretlen érték |
| IS NULL  | NULL ellenőrzés          |
| COALESCE | alapérték NULL helyett   |
# 🔹 Röviden:
A NULL:
👉 „nincs adat az adott mezőben”
* IS NULL ellenőrzés
* COALESCE / IFNULL alapértékhez
👉 A NULL egy speciális állapot, nem egyszerű érték.

91. Mi az a Statement és PreparedStatement JDBC-ben, és mikor érdemes az egyiket a

A **JDBC**-ben a **Statement** és a **PreparedStatement** két módja annak, hogy SQL lekérdezéseket futtassunk egy Java alkalmazásból adatbázis felé.
# 🔹 Statement👉 „Egyszerű SQL futtató eszköz”
* SQL parancsot **szövegként futtat**
* minden alkalommal újra feldolgozza a lekérdezést
Statement stmt = conn.createStatement();
ResultSet rs = stmt.executeQuery(
    "SELECT * FROM users WHERE name = 'Anna'"
Hátrányai:
* **SQL injection veszély**
* lassabb, mert minden futtatáskor újra parse-ol
# 🔹 PreparedStatement

* SQL-t előre előkészíti (precompile)
* paramétereket külön kezeli (`?`)
PreparedStatement ps = conn.prepareStatement(

* **gyorsabb ismételt futtatásnál**

| Statement             | PreparedStatement |
| --------------------- | ----------------- |
| sima SQL string       | paraméteres SQL   |
| lassabb               | gyorsabb          |
| SQL injection veszély | biztonságos       |
| nincs előkészítés     | előre fordított   |
## Statement:
* ritka, egyszerű lekérdezés
* nem dinamikus input
## PreparedStatement:
* felhasználói input esetén (⚠️ kötelező ajánlott)
* ismétlődő lekérdezések
* CRUD műveletek
# 🔹 Röviden:
* **Statement** → egyszerű, de kevésbé biztonságos
* **PreparedStatement** → biztonságos, gyors és ajánlott
👉 A modern Java fejlesztésben szinte mindig a **PreparedStatement** az ajánlott megoldás.

93. Mi a különbség az @OneToMany és az @ManyToOne annotációk között a Hibernate-ben?
A **Hibernate** (és a **JPA**) kapcsolatkezelésében az **@OneToMany** és az **@ManyToOne** annotációk két ellentétes irányú **táblakapcsolatot** jelölnek a Java entitások között.
👉 Ezek relációs adatbázis kapcsolatok leképezése objektumokra.
# 🔹 @ManyToOne👉 „Több gyerek → egy szülő”
* Sok rekord tartozik **egy másik entitáshoz**
* A **FOREIGN KEY** általában itt van
@Entity
public class Order {
    @Id
    private Long id;
    @ManyToOne
    private User user;
👉 Több order tartozhat egy userhez
# 🔹 @OneToMany👉 „Egy szülő → több gyerek”
* Egy entitás **több másik entitást tartalmaz**
* Gyakran a „mappedBy” oldalon van
@Entity
public class User {
    @Id
    private Long id;
    @OneToMany(mappedBy = "user")
    private List<Order> orders;
👉 Egy userhez több order tartozik
| @ManyToOne         | @OneToMany    |
| ------------------ | ------------- |
| sok → egy          | egy → sok     |
| FOREIGN KEY oldala | gyűjtő oldal  |
| Order → User       | User → Orders |
👉 Mindig párban használjuk:
* Order → User (**@ManyToOne**)
* User → Orders (**@OneToMany**)
* A **ManyToOne az „owner side” (tulajdonos oldal)**
* A **OneToMany csak leképezés, nem mindig tartalmaz FK-t**
users:
id | name
orders:
id | user_id (FOREIGN KEY)
# 🔹 Röviden:
* **@ManyToOne** → több gyerek egy szülőhöz
* **@OneToMany** → egy szülő több gyerekkel
👉 Ez a két annotáció együtt modellezi a relációs adatbázis kapcsolatok Java objektumokban való leképezését.

94. Mit jelent a "lazy loading" és a "eager loading" a Hibernate-ben, és mikor érdemes az 
egyiket használni a másik helyett? 
A **Hibernate**-ben a **lazy loading** és az **eager loading** azt határozza meg, hogy a kapcsolt entitások **mikor töltődnek be az adatbázisból** a Java alkalmazásban.
# 🔹 Lazy Loading (lustán betöltés) 👉 „csak akkor töltöm be, amikor tényleg kell”
* A kapcsolt adatok **nem töltődnek be azonnal**
* Csak akkor, amikor először hozzáférsz
@OneToMany(fetch = FetchType.LAZY)
private List<Order> orders;
👉 A user betöltődik, de az orders csak akkor, ha kell
## 🔸 Előnyei:
* gyorsabb induló lekérdezés
* kevesebb memóriahasználat
* hatékony nagy adathalmaznál
## 🔸 Hátrányai:
* **LazyInitializationException** előfordulhat
* több DB lekérdezés fut „később”
# 🔹 Eager Loading (azonnali betöltés)👉 „mindent azonnal betöltök”
* A fő entitással együtt **az összes kapcsolt adat is betöltődik**
@OneToMany(fetch = FetchType.EAGER)
private List<Order> orders;
👉 user + orders együtt töltődik be
## 🔸 Előnyei:
* nincs későbbi DB hívás
* egyszerűbb használat
* nem futsz bele lazy hibába
## 🔸 Hátrányai:
* lassabb lekérdezés
* felesleges adatbetöltés
* nagy memóriahasználat
| Lazy Loading          | Eager Loading                    |
| --------------------- | -------------------------------- |
| késleltetett betöltés | azonnali betöltés                |
| csak szükség esetén   | mindig betölti                   |
| hatékonyabb           | egyszerűbb, de nehezebb skálázni |
## 🟢 Lazy (ajánlott alapból):
* nagy adatmennyiség
* REST API-k
* mikor nem mindig kell a kapcsolat
## 🟡 Eager:
* kis adatok
* biztosan mindig kell a kapcsolt adat
* egyszerű CRUD alkalmazások
# 🔥 Gyakorlati szabály:👉 „Default = LAZY, csak indokolt esetben EAGER”
# 🔹 Röviden:
* **Lazy loading** → csak akkor tölti be az adatot, ha kell
* **Eager loading** → azonnal betölti a kapcsolt adatokat
👉 A cél a teljesítmény és memória optimalizálása az adatmodell szerint.

95. Mi az a cascade attribútum a JPA-ban, és hogyan segíti az entitások közötti kapcsolatok kezelését?
A **JPA**-ban a **cascade** attribútum azt határozza meg, hogy egy entitáson végzett művelet **automatikusan továbbterjed-e a kapcsolódó entitásokra is**. Ezt a Hibernate valósítja meg a háttérben.
👉 „Ha egy objektummal csinálok valamit, akkor a hozzá tartozókat is kezelje automatikusan a rendszer.”
@Entity
public class User {
    @Id
    private Long id;
    @OneToMany(cascade = CascadeType.ALL)
    private List<Order> orders;
👉 Ha a User-t mentjük, az Orders is mentődik
# 🔹 Mire használható a cascade?
## 🔸 1. PERSIST👉 mentés továbbadása
cascade = CascadeType.PERSIST
## 🔸 2. MERGE
👉 módosítások továbbadása
## 🔸 3. REMOVE👉 törlés továbbadása
cascade = CascadeType.REMOVE
👉 User törlés → Orders is törlődik
## 🔸 4. ALL
👉 minden művelet cascaded
cascade = CascadeType.ALL
## 🟢 Előnyök:
* kevesebb kézi adatkezelés
* konzisztens kapcsolatok
* egyszerűbb kód
## 🔴 Hátrányok:
* véletlen adatvesztés (pl. REMOVE cascadenél)
* nehezebb kontroll nagy rendszerekben
* teljesítményproblémák
User user = new User();
user.setOrders(List.of(new Order()));
entityManager.persist(user);
👉 cascade ALL esetén:
* user mentődik
* orders automatikusan mentődik
# 🔹 Kapcsolat más fogalmakkal:
* **@OneToMany / @ManyToOne** → kapcsolat definiálása
* **cascade** → műveletek terjedése
* **fetch (LAZY/EAGER)** → betöltés ideje
# 🔹 Röviden: A cascade azt jelenti, hogy:
👉 az egyik entitáson végzett műveletek automatikusan érvényesülnek a kapcsolódó entitásokon is
* PERSIST → mentés
* REMOVE → törlés
* MERGE → módosítás
* ALL → minden művelet
👉 A cél: egyszerűbb és konzisztens entitáskezelés a JPA-ban.
